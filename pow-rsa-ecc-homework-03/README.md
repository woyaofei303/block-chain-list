# 03 · 哈希、挖矿和签名各解决什么问题

这份实验用 Node.js 标准库完成两件事：找到符合条件的哈希；证明一段文字确实由某把私钥签过。无需区块链节点，也没有资金转移。

## 先分清三个概念

- **哈希**：把任意文字算成固定长度的数字指纹。相同输入得到相同结果，不是可解密的密文。
- **PoW**：反复换输入的一部分，直到指纹满足条件。它证明做过计算，不证明发送者身份。
- **数字签名**：私钥对消息签名，公钥检查签名与消息是否匹配。它不隐藏消息内容，也不是“公钥解密”。

例如输入昵称 `julian`，程序依次计算 `julian0`、`julian1`……直到 SHA-256 的十六进制结果以指定数量的 `0` 开头。`nonce` 就是后面的整数。

多要求一个十六进制零，平均尝试量约乘 16；这只是概率上的平均，不表示每次耗时恰好乘 16。

## 从运行到观察结果

需要 Node.js 20+。从仓库根目录执行，没有第三方依赖，不必先安装包：

```bash
cd pow-rsa-ecc-homework-03/nodejs
npm test
npm start -- julian
```

程序先找 4 个零、5 个零，再对满足 5 个零的“昵称 + nonce”分别做 RSA-2048 和 ECC P-256 签名。两种方案各自生成密钥，不能混用公钥或签名。

预期看到原文验签 `true`，篡改后验签 `false`。把昵称换成自己的名字再跑，nonce 和哈希会变化；耗时还受机器负载影响。密钥只在内存中生成，不打印、不写文件。

## 对照一次完整调用读代码

打开 [main.mjs](nodejs/main.mjs)，先读 `run`，再按以下顺序：

```text
mine → sha256Hex → 得到 nonce 和 hash
“昵称 + nonce” → rsaRoundTrip / eccRoundTrip
生成密钥 → sign → verify 原文 → verify 篡改文本
```

`mine` 去掉昵称首尾空白，拒绝空昵称；难度检查为 1～64，但高难度并不适合实际等待。签名函数把文本转成 UTF-8 字节，同一消息的字节必须一致；多一个空格也属于另一条消息。

[main.test.mjs](nodejs/main.test.mjs) 会复算哈希并检查篡改失败。读测试时关注断言，而不是只看终端打印了“成功”。

## 检查自己是否理解

如果 Bob 拿到原文、公钥和签名，他能检查这段文字是否匹配签名；他不能据此算出私钥，也不能替换成另一段文字后继续使用旧签名。公钥是谁的，仍需另外建立可信身份关系。
